# 五路输出帧率回看

统一启动会默认启动 `frame_monitor`。每次监测启动，在目标设备的
`~/perception_runs/` 创建一个独立目录，使用**该设备本地系统时间**命名，例如：

```text
~/perception_runs/2026-11-06_14-23-08_123456/
    run.json          运行起止时间、实际监测参数、话题、记录完整性
    frames.csv        五路逐帧元数据；默认每 0.1 秒请求硬盘同步
    summary.json      全程计数、间隔、重复/回退时间戳、候选来源关联
    report.html       无外部依赖的交互报告，可直接在浏览器打开
    configs/          本次启动配置快照
```

## 启动和查看

在实际 ROS 2 工作空间重新构建并加载环境（在工作空间根目录运行）：

```bash
colcon build --packages-select my_launch
source install/setup.bash
ros2 launch my_launch system_run.launch.py
```

**保存不依赖 Ctrl+C。** 启动即生成首份 `report.html`，运行中默认每 0.1 秒
同步原始记录、每 5 秒更新离线报告。打开对应目录中的 `report.html` 即可；
报告是保存时的静态快照，重新打开或刷新可查看最新一份。
也可以把整个目录复制到另一台电脑后查看。

正常停止时仍可按一次 **Ctrl+C**，等待终端打印 `Frame-rate report saved:`，
会补存队列中的尾部数据并生成最终报告。突然断电或进程被强杀时，没有这一步，
重启后也能直接打开上次已经保存的报告；下次启动监测器会自动恢复旧运行报告。

目标使用环境为 **Ubuntu + Firefox**。文件管理器中用 Firefox 打开即可，
也可以在终端执行（替换为实际生成的目录）：

```bash
firefox ~/perception_runs/2026-11-06_14-23-08_123456/report.html
```

HTML 中已包含全部数据、绘图和交互逻辑，直接打开本地文件即可，
不依赖网络、浏览器插件、网页服务或 Windows 组件。

可选参数：

```bash
ros2 launch my_launch system_run.launch.py frame_monitor_output_root:=/home/dian/frame_rate_runs
ros2 launch my_launch system_run.launch.py enable_frame_monitor:=false
ros2 launch my_launch system_run.launch.py input_topic:=/other_lidar_points
```

雷达输入话题与模型同步使用 `input_topic`；相机话题、消息类型和 YOLO 上限
从统一启动实际加载的 `yolo_detector.yaml` 读取。
监测器默认的三个输出话题及缓存深度可在 `configs/frame_monitor.yaml` 修改。
运行记录不写入代码目录，不会与原来的 `fusion_debug` 展示数据混合。

也可以在启动感知系统前单独启动监测器（适用于希望预留发现时间的情况）：

```bash
ros2 run my_launch frame_monitor --ros-args -p output_root:=/home/dian/frame_rate_runs
```

此时关闭统一启动中的监测器，避免两份重复记录；单独启动时根据实际情况
覆盖 `lidar_topic`、`camera_topic`、`camera_compressed` 和 `yolo_max_fps`。
独立模式的 `yolo_max_fps` 仅为报告注释，必须与真实配置核对。

## 阅读报告

- 时间轴 `0 s` 是**监测器初始化时刻**，包含后续模型加载和首次发现等待。
  目录名称使用系统时间；运行时长和消息接收间隔使用单调时钟，避免系统校时跳变。
- 拖动滑块、输入时刻或点击曲线，查看 `(t-W, t]` 的五路频率。
  起始区间包括 `0`；不足一个完整窗口时按实际经过时间计算，并明确标注。
  `t=0` 没有可计算时长，显示 `—`。
- 五路卡片显示窗口帧数、最大静默时间、距上一帧时间；逐帧时间条可局部放大。
  窗口最大静默包含窗口两端的无消息区间，与“两个相邻消息的完整间隔”不同。
- 卡片另显示最近最多 100 个接收间隔的均频，计算为
  `间隔数 / (最后一帧接收时间 - 第一帧接收时间)`，便于与 `ros2 topic hz` 对照。
  它不包含最后一帧之后的静默；窗口帧率包含这段静默，因此两个数字可能不同。
  CLI 的样本窗口、时钟和 QoS 也需对齐后再比较，不能直接把长时间均频与某一秒相比。
- 长间隔阈值默认是本路全程帧间隔中位数的 3 倍，可切换；启动等待单独列出。
  没有长间隔不代表帧率达标，应同时比较输入输出频率与配置目标。
- 选择数据流，点击窗口内一帧，查看全程范围内**相同采集时间戳**的同链路候选。
  不会因为输出晚于当前窗口而直接判为缺帧。相机和雷达不做时间戳相等匹配。
- 空检测消息计为一帧；YOLO 调试图、RViz Marker 和调试 CSV 不作为输出帧率来源。

`frames.csv` 中 `elapsed_ns` 为相对监测起点的接收时间，`receive_system_ns`
为系统时间，`receive_ros_ns` 为监测器 ROS 时钟读数；`source_sec` 和
`source_nanosec` 保留原始 Header，纳秒不经浮点数转换。本路 `sequence`
为监测器本地接收计数，不是硬件帧编号。CSV 记录顺序为单线程回调顺序。

若需要记录回放中的 ROS 时钟，可加 `frame_monitor_use_sim_time:=true`。
帧率和滑块始终表示**实际经过时间**；暂停、倍速和循环回放会改变观测频率。
本版没有按 bag 数据时间切换的时间轴。不能直接用回放采集戳和当前系统时间
相减来声称真实传输延迟。

## 持续保存、意外下电与恢复

默认流程全部运行在后台，使用单调墙钟，因此 `/clock` 暂停也会继续保存：

1. 启动时持久保存 CSV 表头、`run.json` 及第一份 HTML。
2. 每 0.1 秒对 CSV 执行 `flush` 和 `fsync`，随后持久保存检查点。检查点包括
   CSV 字节边界、各路已写帧数、已知运行时长、队列长度及当时的监测丢弃计数。
3. 每 5 秒根据最近已提交检查点生成 `summary.json` 和 `report.html`。
   每个文件先写同目录临时文件并同步，再原子替换，随后同步目录项。
   更新期间意外停止时，上一份完整报告仍可保留，临时文件不作为正式报告读取。
4. 下次启动监测器时，后台检查同一输出根目录下未正常结束的旧运行，利用
   操作系统文件锁跳过仍在运行的监测器。可恢复的旧运行重建报告并标记为
   `interrupted`，不修改/截断原始 CSV，也不假定发生的一定是断电。

报告可能落后于原始记录。意外中断后，保存的 HTML 会注明“运行中生成的持久快照，
未确认正常结束”，不会假装它是完整最终结果。自动恢复或手动重建可纳入
CSV 中额外幸存的完整行。若不重新启动监测器，也可手动重建旧目录：

```bash
ros2 run my_launch frame_report /home/dian/frame_rate_runs/2026-11-06_14-23-08_123456
```

也可以用标准 Python（无需 ROS、第三方包）在源码包可导入时运行：

```bash
PYTHONPATH=/path/to/fusion/my_launch python3 -m my_launch.frame_report /path/to/run
```

中断恢复时报告标明“结束时刻未知”，时间轴截至最后恢复的记录/保存检查点，
不会把重新开机的等待时间算进上一段运行。无消息时检查点仍会推进，能够保留
断电前已观测的静默区间；检查点之后的情况未知，不会编造真实断电时刻。
损坏/不完整 CSV 行会跳过并计数。现存数据少于检查点记载时，报告明确提示缺行
或缺字节。报告生成失败时，之前的完整报告及原始记录仍可独立用于恢复。

可在 `configs/frame_monitor.yaml` 中调整：

```yaml
sync_interval_seconds: 0.1
report_interval_seconds: 5.0
```

**0.1 秒是目标同步周期，不是“最多只丢 0.1 秒”的承诺。** 调度延迟、积压队列、
存储变慢/故障都会扩大未保存尾部；增大同步频率也会增加 I/O 开销。
文件系统和存储设备还必须正确执行同步请求。没有掉电保护的存储硬件、设备损坏
或文件系统损坏仍可能造成数据损失。若要求硬断电也不丢任何一帧，仅靠软件定期
写盘无法保证，需要 UPS/供电保持或具有掉电保护的存储，并进行真实断电验证。

与 0.5 秒相比，0.1 秒把目标同步频率从约 2 次/秒提高到约 10 次/秒。
每个检查点会同步 CSV、替换检查点 JSON 并同步目录，实际 I/O 开销并不只是一行
CSV 的大小。同步在后台写盘线程执行，订阅回调不等待；但慢存储会造成监测队列
积压，共享存储/CPU 负载也可能影响整体调度。请在目标设备比较开关监测时的帧率、
处理延迟和检查点队列长度，不应直接假定 0.1 秒一定能稳定达到。
HTML 报告仍每 5 秒更新，避免每 0.1 秒重建整份报告；报告可晚于原始数据。

## 统计边界和目标设备验证

这是第一阶段的**独立订阅监测器**：监测器实际收到的频率不等于生产节点内部
发布次数。它使用兼容 Reliable/Best Effort 发布端的 Best Effort 订阅，深度默认 10。
原始订阅仅解析 CDR1 开头的时间戳，不反序列化完整图像或点云，也不保存载荷；
但 DDS 仍需传输完整消息，仍会有带宽、内存与 Python 字节复制开销。
应在目标设备比较开启/关闭监测时的性能，再决定缓存深度或进一步内部埋点。
未支持的序列化格式会记录为 `unsupported_cdr`，仍计入接收帧率，不用于关联。

后台队列满时只丢弃**监测元数据**，不阻塞感知线程；`run.json` 会保存分路丢弃
计数，报告标记不完整。磁盘故障也会记录；无法继续写磁盘时终端会报错。
监测队列无丢弃不能证明 DDS 没漏收。

运行期间的 CSV 解析、统计、JSON 编码和 HTML 生成现在在**独立进程**执行，
减少其与 Python 接收回调争用 GIL 的机会。采集仍为一个 Python 节点订阅多路原始
消息，并不能据此保证接收不漏帧。磁盘和 CPU 仍为共享资源，需实际对照验证。

若报告低于同一次回放的 `ros2 topic hz`，可先仅监测原始雷达，避免同时订阅大图像：

```bash
# 先关闭统一启动中的监测器，避免重复监测。
ros2 run my_launch frame_monitor --ros-args -p enabled_streams:="['lidar_raw']"
```

此模式仍保存相同格式的运行目录，其他数据流明确标为“未监测”。对照同一回放、
同一话题及稳定运行时段，检查新卡片中的“间隔均频”和命令行测量是否接近。
`run.json` 的 `received_counts` 是监测回调计数，`frames.csv` 是实际保存记录；
两者结合队列丢弃和积压信息可以帮助区分接收问题和保存问题。

当前 YOLO 是限频和最新帧覆盖设计；输入高于配置上限时，未处理每张图是预期行为。
本版**不记录节点内部的覆盖、处理开始/发布事件、融合配对和超时原因**，
因此“未观测到相同采集戳”不能直接解释为异常丢帧。需要这些归因时再补内部事件。
重复采集戳、时间回退、bag 循环可能导致候选不唯一，报告明确标记。

当前 Map 按雷达检测到达发布，相机后台更新颜色；Map 帧率正常不证明相机持续参与。
启动过程的进程启动顺序不保证 DDS 已完成发现；停止时各节点同时收到退出信号，
监测器不保证收齐其他节点尚未发布的在途结果。不要将首尾候选直接计为异常丢帧。

目标设备至少检查：五路消息均可收到；空检测仍计帧；短暂停止某路可定位空白；
运行期间无需停止就能看到更新的 CSV/HTML；强杀监测进程后报告可打开；
下次启动可恢复旧运行；离线报告和时间戳关联符合实际。
仓库自动检查使用人工构造事件，并包含子进程强杀恢复测试；这些不代表实车采样、
Ubuntu ROS/Firefox 运行验证或物理掉电测试。真实断电验证应在可恢复的测试设备上进行。
